# Skill Builder —— Claude Code Skill 编写助手

## 触发条件

当用户提出以下任一需求时调用此 Skill：
- "写一个 Skill" / "创建一个 Skill" / "帮我写 Skill"
- "新建技能" / "写个技能" / "生成 Skill 文件"
- "这个功能能不能做成 Skill"
- 用户描述了想让 AI 自动完成的某类重复任务

## 核心能力

作为元技能（Meta-Skill），本 Skill 帮助你从零开始创建结构完整、质量可靠的 Claude Code Skill：

1. **需求提炼**：从自然语言描述中提取 Skill 的核心功能和触发场景
2. **模板生成**：按标准结构生成 `skill.md` + `references/` 目录
3. **质量校验**：自动检查 skill.md 的必要章节是否齐全、规则是否明确
4. **参考引擎**：如需数据处理/分析类 Skill，同步生成 `references/` 下的规则手册和分析脚本

## 工作流程

### Phase 1: 需求澄清

从用户的描述中提炼以下信息，**如任一字段缺失则主动提问澄清**：

```
【Skill 基本信息】
名称：<中文短名，作为文件夹名>
触发词：<用户说什么时触发？列出 3-5 个典型触发句>
一句话描述：<这个 Skill 做什么？>
```

> **原则**：不要猜测——缺失的关键信息必须向用户确认。但如果有合理默认值（如名称从上下文推断），可以给出推荐并询问确认。

### Phase 2: 结构规划

规划 Skill 的文件结构。根据复杂度分两档：

**简单 Skill**（纯文本/流程指引，无数据处理）：
```
.claude/skills/<名称>/
└── skill.md          # 单文件即可
```

**复杂 Skill**（含数据获取、算法分析、外部工具调用）：
```
.claude/skills/<名称>/
├── skill.md          # 主文件
└── references/
    ├── rules.md      # 规则手册（可选但推荐）
    └── <引擎>.js     # 分析/处理引擎（如需要）
```

> 在生成前向用户确认文件结构。对于简单 Skill 不要过度设计。

### Phase 3: 编写 skill.md

按以下标准骨架编写（**所有标记为"必填"的章节不可省略**）：

```markdown
# <Skill 中文名称>

## 触发条件 (必填)
<!-- 当用户提出以下任一需求时调用此 Skill： -->
<!-- - 具体触发场景 1 -->
<!-- - 具体触发场景 2 -->
<!-- 需要明确列出关键词和句式 -->

## 核心能力 (必填)
<!-- 用 3-5 条精炼描述这个 Skill 能做什么 -->

## 执行步骤 (必填)
<!-- Step 1 / Step 2 / ... 每个步骤包含具体指令、命令或代码 -->

## 关键规则 (有业务规则时必填)
<!-- 规则表格或列表，标注"不可违反"或"推荐" -->

## 注意事项 (推荐)
<!-- 边界条件、坑点、数据源说明 -->

## 免责声明 (涉及外部数据/建议时必填)
<!-- 仅在适用时添加 -->
```

### Phase 4: 编写 references（按需）

**rules.md 模板**——当 Skill 涉及：
- 复杂的分区/分类规则
- 数学公式或阈值判断
- 外部 API 调用约定
- 需要脱离 Skill 对话也能查阅的参考文档

**引擎脚本模板**——当 Skill 需要：
- Node.js/Python 数据计算
- 重复执行的复杂逻辑
- 可在 Skill 调用中直接 `node xxx.js` 执行

### Phase 5: 质量校验

生成全部文件后，对照以下检查清单逐项验证：

#### skill.md 校验清单

| # | 检查项 | 标准 |
|---|--------|------|
| 1 | 触发条件明确 | 列出 ≥3 个具体触发场景或关键词 |
| 2 | 核心能力清晰 | 3-5 条，每条约 15 字以内 |
| 3 | 执行步骤可操作 | 每个 Step 包含可执行的命令/代码/决策逻辑 |
| 4 | 规则不模糊 | 无"根据需要"、"酌情"等模糊词，阈值和参数明确 |
| 5 | 边界条件覆盖 | 对异常/边界情况有处理说明 |
| 6 | 不重复 | 与已有 Skill 不重叠（检查同名目录） |
| 7 | 文件可读 | Markdown 格式正确，表格对齐 |

#### references 校验清单（如生成了 references）

| # | 检查项 | 标准 |
|---|--------|------|
| 8 | rules.md 自洽 | 阈值、分区等定义与 skill.md 一致无矛盾 |
| 9 | 引擎语法正确 | `node --check xxx.js` 通过 |
| 10 | 引擎可独立运行 | 填充数据后能正常输出（不依赖 Skill 上下文） |

## Skill 编写最佳实践

### DO ✅

- 触发词要**具体且覆盖全面**，既有关键词也有完整句式
- 规则用**表格**而非段落，一目了然
- 数字参数**写死**不要留"适当"、"酌情"余地
- 分拆复杂逻辑到 `references/`，保持 `skill.md` 精炼（< 150 行）
- 涉及外部 API 时注明**请求方式、参数、返回格式**
- 输出格式在 skill.md 中**写死章节标题**，确保每次调用输出一致

### DON'T ❌

- 不要把整个分析脚本嵌入 skill.md（应放 references/ 下）
- 不要用"可能"、"也许"、"大概"等不确定用语定义规则
- 不要让两个 Skill 的触发词高度重叠导致误触发
- 不要省略免责声明（涉及外部数据、建议类 Skill）
- 不要写无法执行的模糊指令（"分析一下数据" → 应该写"运行 `node analyze.js`"）
